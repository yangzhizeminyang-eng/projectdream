# 受控竖屏终剪真实闭环验证记录

## 1. 目的

本记录验证一条恢复候选能否在不批量消费任务、不替代人工审美签核的前提下，完成：

```mermaid
flowchart LR
  A[COS 抽帧复核] --> B[保存人工复核结论]
  B --> C[单条明确确认终剪]
  C --> D[Worker 单素材渲染]
  D --> E[ffprobe 技术质检]
  E --> F[自动质量报告]
  F --> G[人工质量签核]
  G --> H[发布合规包]
```

验证对象为项目 `12` 的恢复候选 `videoId=193`。这是无实体人物的广播机镜头，因此不把“空镜头通过”伪装成角色外貌一致性已验证。

## 2. 执行边界

- 只允许处理 `videoId=193`。
- 不批量消费其他 `generation_jobs`。
- 不自动确认候选为分镜主版本。
- 不删除 COS 源视频、抽帧证据或失败导出。
- 不伪造人工画面、字幕、音频签核，也不宣称已经可以稳定发布或稳定盈利。

## 3. 真实执行过程

### 3.1 人工复核

对 COS 中的 3 张抽帧进行复核。画面为旧广播机、红色指示灯和冷蓝环境，连续性可接受；来源静帧快照标记为 `characterFree=true`，没有预期实体角色。

复核结果通过真实接口保存为 `approved`，备注明确为“用户授权的执行代理依据 3 张 COS 抽帧复核”，没有写成真人到场复核。

### 3.2 第一次执行发现范围错误

首次创建的导出 `exportId=28` 意外走入普通 `hybrid-mvp` 分支，处理了整个项目：

| 项目 | 实际结果 | 是否合格 |
| --- | --- | --- |
| 源片段数 | 57 | 否 |
| 成片时长 | 191.34s | 否 |
| 流水线 | `hybrid-mvp` | 否 |

该任务没有进入签核或发布，而是通过明确确认的回滚接口标记为 `canceled`。媒体对象和源候选均保留，供审计。

根因是 `isRecoveryFinalEditExport(config)` 只读取数据库行的 `config_json` 字段；Worker 传入已解析的配置对象时函数返回 `false`，导致走普通项目混剪。

### 3.3 第二次执行发现运行环境错误

修复范围识别后，`exportId=29` 正确保持单条配置，但在渲染前失败：

```text
no usable video or static frame clips
```

根因是 API/Worker 只加载 `.env.local`，而 `videoId=193` 的源视频位于 COS。此时生成的地址落到本地对象存储并返回 404。

修复措施：

1. `server` 和 `worker` 均加载 `.env.local`，并用 `--env-file-if-exists=.env.production` 读取存在时的 COS 配置。
2. 增加启动配置合同测试，防止 API 与 Worker 的对象存储环境再次不一致。
3. 回滚接口支持 `failed` 状态，释放失败任务的幂等键后才允许显式重试。

`exportId=29` 已回滚为 `canceled`，未删除任何媒体。

## 4. 修复后的关键保护

### 4.1 恢复终剪身份识别

恢复终剪既识别标准 `pipeline=recovery-final-edit-v1`，也校验：

- `recoveryFinalEdit.version=1`
- `sourceMode=single-recovery-candidate`
- `planId=recovery-final-edit-video-{videoId}`

因此即使普通分支错误覆盖 `pipeline`，系统仍能识别其为恢复终剪，允许审计回滚并恢复专用流水线标识。

### 4.2 单条边界

Worker 对恢复终剪调用 `buildRecoveryFinalEditPayload`，只返回一个 `videoTrack.items` 条目。完成态必须保留：

```text
sourceClipCount=1
pipeline=recovery-final-edit-v1
```

这两项是防止再次混入全项目镜头的核心验收字段。

### 4.3 失败可回滚、重试仍需明确确认

`queued`、`running`、`completed`、`failed` 四种恢复终剪状态都可通过精确口令回滚。回滚只：

- 更新状态为 `canceled`；
- 清空数据库 `idempotency_key`；
- 写入回滚时间；
- 保留候选、导出文件和审计配置。

后续重试仍必须重新调用单条执行接口并提供 `START_RECOVERY_FINAL_EDIT`。

## 5. 当前发布结论

`exportId=31` 是“自动技术门禁合格的单条竖屏终剪样片”，但它还不是可直接发布并稳定赚钱的内容。

当前发布合规包真实状态为 `blocked`，阻塞项：

1. 画面、字幕、音频三项人工质量签核未全部批准。
2. AI 生成标识尚未按目标平台规则确认。
3. 目标平台字段、版权字段和发布当天规则仍需人工核验。
4. 还没有 10 条受控终剪回归和三集试制数据，不能证明稳定生产或稳定收入。

此外，发布当天仍必须人工核验红果、抖音等官方后台的最新规则、版权字段和 AI 标识要求。

## 9. 语音源预检补强

复查 `exportId=30` 配置发现，样片对应分镜已有已确认对白 `audioAsset=120`，但 Worker 下载该资产时返回 `HTTP 404`，所以 `boundAudioCount=0`。旧流程仍会加入静音底轨并完成渲染，最终才在成片响度检查发现静音。

现已改为：

1. 对本条终剪实际需要混入的对白/旁白逐个下载。
2. 下载成功后先用 `loudnorm` 检测源音频是否存在可测声音。
3. 下载失败、检测静音或无法判断声音时，在混音、成片上传和 `completed` 写回前直接失败。
4. BGM/SFX 仍按原授权门禁处理；本规则只强化不能缺失的对白和旁白。

随后已使用只读 COS `HeadObject` 检查确认 `audioAsset=120` 的对象缺失，旧本地音频目录也没有对应文件，因此不存在可安全回填的源文件。当前已通过单条 TTS 重生成得到 `audioAsset=169`，并用 `EXPORT_WORKER_ONLY_EXPORT_ID=31` 完成受控重剪；后续重点转为人工终审、发布合规包和 10 条受控回归。

## 10. 返工候选的下一步动作门禁

恢复候选一旦被人工标记为 `rework`，任务中心不得继续展示“执行终剪”作为主要动作。当前实现会：

1. 汇总视频级返工备注和逐角色返工备注，形成结构化 `reworkReasons`。
2. 输出 `nextAction.code=regenerate-recovery-candidate`，明确下一步是重新生成候选。
3. 继续保持 `finalEditReadiness.status=blocked-by-rework`，不会因为存在终剪计划而放行。
4. 点击“重新生成候选”只返回当前场景的视频生成页，由人工决定参数并再次提交单条生成；本次导航不启动模型、不创建恢复队列任务。

该门禁用于防止横版候选在返工原因尚未解决时直接进入竖屏终剪，也避免把“人工复核已保存”误解为“已经可以发布”。
